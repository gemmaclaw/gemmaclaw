# Site Architecture

The Gemmaclaw site at `gemmaclaw.github.io/gemmaclaw` is a multi-page static site generated by a single Python script and deployed via GitHub Pages. No build tools, no frameworks, no server required.

## Page Structure

| File                     | Purpose                                                  | Content Source                                                                       |
| ------------------------ | -------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `site/index.html`        | Landing page, hero section, card links to all subpages   | Static content in `generate_index_page()`                                            |
| `site/setup.html`        | Full setup guide with CLI reference                      | Static content in `generate_setup_page()`                                            |
| `site/self-hosting.html` | Hardware configuration guide, search, backend comparison | Dynamic from `benchmark-results/` via `generate_hardware_guide_cards()`              |
| `site/benchmarks.html`   | Benchmark results grouped by model size class            | Dynamic from `benchmark-results/` JSON files                                         |
| `site/community.html`    | Reddit community reports, field notes                    | Dynamic from `site/data/gemma4-hardware-configs.json` and `site/data/field-notes.md` |
| `site/goals.html`        | Three-phase roadmap and progress                         | Static content in `generate_goals_page()`                                            |

All pages share the same nav bar, footer, CSS, and responsive layout via the `page_template()` function.

### URL Scheme

All pages are flat `.html` files at the site root. No subdirectories, no hash routing, no client-side routing.

- `index.html` (home, default)
- `setup.html`, `self-hosting.html`, `benchmarks.html`, `community.html`, `goals.html`

Nav links point to page files (e.g. `href="setup.html"`), not anchor scrolls.

## Design Decisions

### Multi-page vs SPA

Static multi-page HTML was chosen over a single-page app because:

1. **GitHub Pages compatibility**: no server, no build step at deploy time. The `site/` directory is uploaded as-is.
2. **Simplicity**: each page is a self-contained HTML file. No JavaScript framework, no routing library, no hydration.
3. **SEO and shareability**: each page has its own URL, title, and meta description.
4. **Performance**: pages load only their own content. The benchmarks page (with large tables) does not bloat the landing page.

### Nav Pattern

Sticky top nav with scrollable links on mobile. The `Gemmaclaw` logo links to `index.html`. Active page is highlighted with a blue underline via the `active` CSS class set by `page_template()`.

### CSS Theme

All styling is inlined in each page via the `CSS` string constant in `generate-site.py`. No external stylesheet. CSS custom properties (variables) control theming:

- `--bg: #ffffff` (white background, light theme)
- `--accent: #4285f4` (Google blue for interactive elements)
- `--good / --warn / --bad` for benchmark score coloring
- `--bg-elev / --bg-elev-2` for card and section backgrounds

### Mobile Approach

- Max content width: 960px, centered
- Nav links scroll horizontally on narrow viewports (no hamburger menu)
- Tables use `overflow-x: auto` wrappers for horizontal scroll
- Cards stack vertically on mobile via flexbox wrap

## Content Guidelines

### Tone and Depth

The site targets someone new to Gemma who wants to go from zero to running benchmarks. Content should be:

- Practical and direct. Lead with what the user needs to do.
- Technically accurate. Include exact commands, flags, and expected output.
- Self-contained per page. Assume the reader landed on this page directly.

### Content Per Page

- **Setup**: full CLI reference with every command, flags, examples, expected output. Installation for all platforms (Linux, macOS, WSL2, Docker). Troubleshooting section.
- **Benchmarks**: size class grouping with hardware requirements, detailed test case explanations, methodology, how to interpret scores.
- **Self-Hosting**: hardware cards with search/filter, backend comparison table (Ollama vs llama.cpp vs Gemini), deployment tiers.
- **Community**: Reddit reports with category filters, curated field notes. Each report links to original post.
- **Goals**: three-phase roadmap (Evidence, Productization, Community Loop) with status per milestone.

### Adding a New Page

1. Define a `generate_<name>_page()` function in `generate-site.py` that returns HTML via `page_template()`.
2. Add the page to the `NAV_ITEMS` list (label, filename, is_external flag).
3. Add the filename to the `pages` dict in `generate_site()`.
4. Add the filename to `REQUIRED_PAGES` in `check-site-quality.sh`.
5. Add a card link on the index page in `generate_index_page()`.
6. Regenerate: `python3 scripts/site/generate-site.py`.
7. Commit both the generator and the generated `site/*.html` files.

## Generator Architecture

### File: `scripts/site/generate-site.py`

Single Python script (~1900 lines), no external dependencies. Runs with Python 3.8+.

### Key Components

| Component                  | Lines           | Purpose                                                                      |
| -------------------------- | --------------- | ---------------------------------------------------------------------------- |
| `load_benchmark_results()` | Data loader     | Reads `benchmark-results/*/results.json` files                               |
| `best_results()`           | Deduplication   | Returns best result per model/backend combo                                  |
| `classify_model_size()`    | Classifier      | Maps model names to size classes (Small 4B, Medium 27B MoE, Large 31B Dense) |
| `SIZE_CLASSES`             | Config dict     | Defines model patterns, hardware recommendations, icons per size class       |
| `page_template()`          | Layout wrapper  | Generates full HTML document with nav, footer, CSS for any page content      |
| `generate_*_page()`        | Page generators | One function per page, returns HTML body content                             |
| `generate_site()`          | Orchestrator    | Loads all data, calls page generators, writes files to `site/`               |
| `CSS`                      | Style constant  | All CSS inlined as a Python string constant                                  |
| `NAV_ITEMS`                | Nav config      | List of (label, href, is_external) tuples                                    |

### Data Flow

```
benchmark-results/*/results.json  -->  load_benchmark_results()
                                          |
                                    best_results() --> deduped list
                                          |
                              +-----------+-----------+
                              |           |           |
                    size_class_sections  task_explanations  hw_cards
                              |           |           |
                         benchmarks.html  |      self-hosting.html
                                          |
site/data/gemma4-hardware-configs.json --> community_cards
site/data/field-notes.md               --> field_notes_html
                                          |
                                     community.html
```

### Where to Add New Sections

- **New benchmark metric**: modify `generate_benchmark_table_rows()` and the table header in `generate_benchmarks_page()`.
- **New community data source**: add a loader function similar to `load_community_configs()`, wire it into `generate_site()`.
- **New size class**: add an entry to the `SIZE_CLASSES` dict.
- **New setup command**: add to the static HTML in `generate_setup_page()`.

## Deployment

### Workflow: `.github/workflows/deploy-site.yml`

Triggered on push to `main` when `site/**`, `scripts/site/**`, or `benchmark-results/**` change. Also triggerable manually via `workflow_dispatch`.

Steps:

1. Checkout repo.
2. Run `check-site-quality.sh` (regression checks for missing pages, broken markup, navigation issues).
3. Upload `site/` directory as a Pages artifact.
4. Deploy to GitHub Pages.

### What the `site/` directory contains

The committed `site/` directory is the source of truth for deployment. The deploy workflow serves the committed files directly. It does NOT regenerate the site during deploy.

This means: after changing the generator, you must regenerate and commit both:

```bash
python3 scripts/site/generate-site.py
git add scripts/site/generate-site.py site/
git commit -m "site: description of change"
```

### Quality Checks: `scripts/site/check-site-quality.sh`

Runs as part of the deploy workflow and can be run locally. Checks:

- All required pages exist (`index.html`, `setup.html`, etc.)
- No raw Markdown artifacts in HTML output
- No bare URLs in community card summaries
- Key content sections present in each page (checks for `id="setup"`, `id="benchmarks"`, etc.)
- Navigation present in all pages
- Nav links point to pages, not anchor scrolls
- Community filter bar present when cards exist
